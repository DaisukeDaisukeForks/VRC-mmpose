# RTMW3D-X ブラウザ全身3Dトラッキング・距離推定・SteamVR/VRChat送出 完全版企画書
作成日：2026-11-01
状態：設計・公開実装調査済み／実装と実機ベンチマークは未実施
基準：これまでのRTMW-l 384×288ブラウザPoC仕様を継承し、主モデルを指定済みの`Soykaf/RTMW3D-x`へ変更する。特に絶対位置・奥行き・前後移動を必須機能へ格上げする。
## 0. エグゼクティブサマリー
カメラを即時購入せず、iPad Air M4で撮影した動画から始め、PCのChrome/EdgeでONNX Runtime WebのWebGPUを使って全身133点の3D骨格を推論する。次に既存のiPad Air M4とHuawei P20 LiteからLAN内WebRTCで映像を取り込み、最後に必要性が確認できた場合だけWaveshare 4MP USBカメラ3台へ拡張する。動画PoCはGitHub ActionsでGitHub Pagesへ公開し、同じ静的アプリを127.0.0.1からも利用可能とする。Node.jsは推論ではなくHTTP/WSS、同期・統合・補正およびSteamVR送出の通信・状態管理を担当する。
**重要な定義：RTMW3D-Xの`z`は原則として骨盤基準の相対奥行きであり、人物全体のカメラからの絶対距離ではない。** 相対奥行きにカメラの内部・外部校正、本人の身長と骨長、画面上の2D関節座標、床接地、時系列を組み合わせ、人物のワールド座標`(X,Y,Z)`を別途求める。これを実装しない限り「3Dポーズ推論成功」と「VR空間内での移動追跡成功」を同義にしない。
## 1. 確定要件・設計境界
- 主モデル：`https://huggingface.co/Soykaf/RTMW3D-x`に公開された**RTMW3D-X 384×288 ONNX**。モデルを勝手にRTMW-l（2D）、RTMW3D-L、DWPose等へ差し替えない。代替モデルは別計測・比較用に限る。
- 実行エンジン：ブラウザの**`onnxruntime-web/webgpu`**。`onnxjs@0.1.8`は使用しない。WASMは互換性診断用に限り、60fps達成結果と混同しない。
- 対応GPUの下限目標：**RTX 5060 Ti 8GB**。VRAM8GBでの動作、WebGPU対応、モデルロードと継続60fpsは**未実測**であり、達成済みと記載しない。
- 初版：**動画ファイル入力のみ**。`getUserMedia()`、WebRTC、USBカメラ処理を初版の完成条件に入れない。動画を通常速度で再生しながら推論fpsを測る。動画1秒を1秒以内で処理できるかの検査と、録画動画を速度無制限で処理するベンチは区別する。
- 最終必須機能：3D関節に加え、人物全体の前後・左右・上下移動、床基準位置、歩行・しゃがみ・ジャンプ、腰・両足等の位置・方向を推定し、Node.jsからSteamVRの仮想トラッカーへ送出する。VRChat上での利用はHMDとの座標合わせとFBTキャリブレーションを含む個別の完成条件とする。
- 人物切り抜き：背景の透過・セグメンテーションを必須とせず、人物検出／追跡／手動ROI／見切れ対応を優先する。
- カメラ：機種・解像度・fps・画角・設置位置を購入前に固定しない。3台購入費用の支出はフェーズ2での実測判断まで保留する。
- 通信：外部へ送るのは初回の公開静的ファイル・モデル等を取得するリクエストだけに限定する設計と、**実行時に外部通信を一切許さない閉域モード**を明確に分離する。動画・カメラ映像・姿勢データはクラウドへアップロードしない。
- 表示用アバター：所持または正当に利用できるずんだもんの3Dモデルを読み込める仕様とする。**アバターの身長・骨格はユーザー実寸の測定値に流用しない**。モデル本体の再配布許諾も別確認する。
## 2. 事前調査で確定した技術的事実
### 2.1 指定モデルと実行例
- Hugging Faceの`Soykaf/RTMW3D-x`はApache-2.0表記のONNX変換済み配布物で、`onnx/rtmw3d-x_8xb64_cocktail14-384x288-b0a0eab7_20240626.onnx`を含む（表示サイズ約369MB）。ダウンロード先：`https://huggingface.co/Soykaf/RTMW3D-x/resolve/main/onnx/rtmw3d-x_8xb64_cocktail14-384x288-b0a0eab7_20240626.onnx`。**配布サイト掲載のSHA-256は`4a289c0e99d47eb595e99679d9d4a2d1def1b4241f9adcbafba44b9ff585ebcd`**。実装時には取得ファイルを計算して照合し、入力名・出力名・形状も記録する。これは、ハギングフェイスの公開ダウンロードAPIで直接フェッチし、サービスワーカーにオリジン単位でキャッシュするべきである。しかしながら、ローカルホストではWebRTCとサービスワーカー要件を満たせないため、実装者は大いに検討しなければならない。
- Harvard EZ-MMLA ToolkitではブラウザのONNX Runtime WebでRTMDet-sを用いた人物BBox検出、288×384への人物ROI切り抜き、RTMW3D-XによるX/Y/Z SimCC推論を実施している。これはブラウザでの技術的実現性の参考実装だが、RTX 5060 Tiで60fps・絶対距離追跡が達成済みという証拠ではない。
- MMPose公式`RTMW3D-X`設定は`num_keypoints=133`、画像入力幅288×高さ384、`SimCC3DLabel`（Zを含む）、`root_index=(11,12)`。3D推定のX/Y/Zと、部屋のワールド座標・人物の絶対移動は異なる概念である。
### 2.2 なぜRTMW3D-Xだけで絶対距離が出ないか
- MMPoseの`simcc_3d_label.py`では、教師3D座標のZから両股関節の平均Zを引いて相対深度を作り、Zを分類形式へ符号化する。復号後のZは概ね**骨盤を基準とするメートル単位の前後関係**である。
- 実装に`root_z=[5.14388]`という**学習データ由来の固定既定値**がある。`pose_estimator.py`は`relativeZ + root_z`を絶対深度としてカメラ座標へ射影するが、この既定値を実際の撮影距離として用いると、人物が前後に歩いても距離は正しく更新されない。5.14388mをセンサーの測定値として扱うことを禁止する。
- 指定Qiita記事はRTMW/RTMLibで動画の足首・つま先・踵などの**2Dキーポイント**を取得し歩行解析に使う事例。正面・側面動画が扱えることの参考になるが、絶対3D距離やSteamVR連携の検証にはならない。
### 2.3 二種類の「奥行き」を常に別フィールドで保持する
1. `jointRelativeZ[i]`：骨盤基準の、個々の関節が手前／奥にある量。RTMW3D-Xで得る。
2. `rootCameraPosition=(Xroot,Yroot,Zroot)`：カメラから人物の骨盤までの実距離を含む位置。人体尺度・2D像・校正・多視点等から追加で推定する。
3. `worldRootPosition`：床原点を持つ部屋座標での人物の位置。校正済みカメラ姿勢から変換する。
4. `trackerPose`：SteamVRの座標系へ変換した仮想トラッカーの位置・回転。HMDの座標合わせと実装上の追従品質に依存する。
この4段階を混ぜず、UI・ログ・送信データでも区別する。

## 4. 4層アーキテクチャ
```text
[フェーズ1: iPad等で撮影したローカル動画]
                    │
[フェーズ2以降: iPad / Huawei P20 Lite / USBカメラ]
                    │  WebRTC (LANのみ) / PCのUVC
                    ▼
┌ サーバー1: 静的UI + 推論ブラウザ ────────────────┐
│ Node.js静的HTTP(S) worker: Codex online sandbox       │
│ Chrome/Edge本体: sandbox外、onnxruntime-web/webgpu     │
│ RTMDet/ROI → RTMW3D-X → 2D + relative 3D            │
└───────────────────────────────────────────────────────┘
         ▲                │ 2D観測+相対Z+時刻/品質
         │                ▼
┌ サーバー2: カメラ/接続制御 worker ──────────────┐
│ Codex online sandbox: HTTPS/WSS認証、WebRTC信号       │
│ モバイル撮影ページ、端末ペアリング、入力状態管理      │
└───────────────────────────────────────────────────────┘
                          │ 許可済みの親Node IPC
                          ▼
┌ サーバー3: 統合 worker ──────────────────────┐
│ Codex offline sandbox: 時刻補正・距離推定・三角測量  │
│ 校正・接地・IK・欠測・遅延補正・姿勢品質            │
│ 外部ソケットを開かない。親Nodeと限定stdio IPC       │
└───────────────────────────────────────────────────────┘
                          │ 制限済みIPCで検証済み姿勢
                          ▼
┌ サーバー4: ネイティブNode.js ────────────────┐
│ VMT用の座標変換・OSC/UDP送信・デバイス状態管理     │
└───────────────────────────────────────────────────────┘
                          │ 127.0.0.1:39570
                          ▼
                 VMTドライバ → SteamVR → VRChat
```
- これは**4つの責務境界**であり、必ずしも4つのホストPCや外部クラウドサーバーを意味しない。親Node.jsの限定オーケストレータを別途置き、worker間の任意横断通信を許可しない。
- サーバー1・2の「Codex sandbox保護」は**Node.js workerを隔離**する設計である。一般のChrome/Edgeブラウザ本体をCodex sandbox内に入れたことにはならない。
- サーバー3のオフラインworkerはネットワーク受信ソケットへ直接依存させず、親Node.jsとの**長さ制限付きNDJSON stdio**で操作する。センサーデータの内部入力・処理・出力に限定する。
- 添付の`typed-voice-server`にある`codex-sandbox-launcher.mjs`、`sandbox-worker-client.mjs`、`stdio-peer.mjs`、`boundary-probe.mjs`の責務分離を**参考設計**として採用可能。ただし、音声サービスのworkerをそのまま再利用するとは限らない。Windows Codex sandboxのネットワーク遮断・loopback横移動禁止は実行時に毎回probeし、失敗時はfail-closedとする。
- 1台のPC内の`127.0.0.1`通信はルーターを通らず、同一LANのWebRTCも必ずルーターを経由するわけではない。**ルーターへのヘアピン転送で漏えいを防止するという前提は採用しない**。端末ファイアウォール、通信先許可リスト、ルーターのWAN遮断、パケット監査を併用する。
## 5. RTMW3D-Xモデルの契約
- 取得先：`Soykaf/RTMW3D-x`の上記ONNX。Hugging Faceのcommit revisionを固定し、**掲載済みSHA-256と取得したファイルの計算値を照合**する。取得後のローカルキャッシュを許可する。モデルIDとハッシュで監査し、単なる同名ファイルは採用しない。
- 実装：`import * as ort from 'onnxruntime-web/webgpu'`。`InferenceSession.create(model, {executionProviders:['webgpu']})`で初期化し、`session.inputNames`、`session.outputNames`、shapeを実モデルから確認する。WASM fallbackは明示的な診断モードとし、fps記録にもbackendを付ける。
- RTMW3D-Xの入力は**横288×縦384**の人物ROI画像を想定し、NCHW `float32[1,3,384,288]`が一般的。ただし、実際のONNXの定義を正とし、正規化・RGB順・テンソル名の二重適用を避ける。
- 出力はX/Y/Z軸ごとのSimCCである。標準的な比率2ではX=576、Y=768、Z=576の分類ビンが想定されるが、実モデルの出力テンソル形状と順序を確認し、実測値を採用する。前処理と後処理はMMPoseの`SimCC3DLabel`・RTMW3DHeadのコードに整合させる。
- 3D座標の復号はX/Yを元映像のピクセル座標へ戻し、Zだけは骨盤基準の相対メートルへ戻す。Z復号における`z_range`は公式実装の`2.1744869`が既定だが、実変換の設定一致を確認する。
- 実行中のONNX不正、GPUデバイス喪失、RAM/VRAM不足、演算子のWebGPU未対応を個別に扱う。基準となる最小1フレームの公式実装との数値比較を通過してから動画ループを作る。
## 6. 画質・撮影解像度と人物ROI
**原則：必要ない縮小をソフトウェアに追加しない。** カメラや動画から得られた元フレームをそのまま保持し、必要な場合だけモデルの入力領域を切り抜き・リサイズする。低解像度のカメラ出力だけで検出が十分なら全画面縮小は実行しない。
- `sourceWidth/sourceHeight`・撮影方向・回転・鏡像・焦点距離・レンズ歪み・BBoxをクロップ前座標で保持。撮影解像度を変えた場合は内部行列Kの画素スケールを変換する。
- 方式A：画像全体がほぼ1人で構成されている場合は自動BBox検出を省略し、固定ROIで推論。解像度・アスペクト比がモデル入力に一致しており境界も適切なときは再サンプリングさえ不要。
- 方式B：人物が小さい／背景が多い場合はRTMDet-s等の軽量検出器から人物BBoxを得て元画像からクロップ。人物検出用の小さい画像は**検出モデルが必要とする場合だけ**生成する。
- 方式C：動画中のBBoxを時間追跡し、数フレームごとに再検出。追跡失敗時や人物が急移動した場合は即再検出する。bboxの移動・形状変化は距離推定に利用するが、追跡器のBBox揺れを身長変化と誤認しない。
- 方式D：下半身のみ／上半身のみ／見切れでは手動ROI、画面外までの仮想BBox拡張、パディング、可視部位マスクを選択可能にする。「全身検出器が人として認識すること」を必須条件にしない。
- 3D復元では、**クロップ領域上の2D座標をそのままカメラの投影式に使わない**。各関節を元映像ピクセルへ逆変換し、元映像用のKを使う。ROIの拡大率で見かけの身長が変わっても、実際の距離が変化したと誤判定しない。
- 指先・足先の識別率と身体全体の切り抜き精度を分けて測る。元映像で指がほぼ見えない場合は、ソフトウェア拡大で実情報を増やせない。部分ROIや部位別推論の追加は実測から判断する。
- セグメンテーションは背景が検出精度を劣化させる場合の比較候補とし、初版の前提としない。
## 7. 人物までの絶対距離推定：核心設計
### 7.1 校正値（最低限）
- 画角が分かるだけの暫定推定と、チェッカーボード／ChArUco等で実測した内部校正を区別する。内部行列は`K=[[fx,0,cx],[0,fy,cy],[0,0,1]]`、歪み係数`D`、画像サイズで記録する。
- 初期入力：本人身長[m]、推定誤差を許容した骨長（肩－腰、左右大腿、左右下腿、足長等）、カメラの設置高さ・傾き、床原点／床面、任意の既知寸法基準物。
- 固定カメラでは、校正した外部行列`T_world_camera`を保存する。カメラが移動、ズーム、電子手ブレ補正や画角切替したときは校正の有効性を再確認する。
- フェーズ1で内部パラメータが不明な既存動画も入力可能とするが、その場合の結果は**推測値**と明示し、センチメートル精度を宣言しない。
### 7.2 単眼：相対Z＋骨長拘束から骨盤距離を推定
記号：元画像上の関節画素`(u_i,v_i)`、RTMW3D-Xから得た骨盤相対奥行き`dz_i[m]`、骨盤深度候補`Zr[m]`。各関節のカメラ座標は（歪み補正後）次式で復元できる。
```text
Zi = Zr + dzi
Xi = (ui - cx) * Zi / fx
Yi = (vi - cy) * Zi / fy
Pi = (Xi, Yi, Zi)
```
モデルが相対Zを出しても、**Zrが未知のままではカメラからの前後距離が定まらない**。候補Zrを探索・最適化し、モデルの推定骨長と本人の既知骨長が最も整合する距離を選ぶ。具体的な目的関数は以下とする。
```text
E(Zr) = Σ_b wb * ρ( |Pi(Zr)-Pparent(b)(Zr)| - Lb )
      + λfloor * E_floor(Zr)
      + λtime  * E_temporal(Zr)
      + λprior * E_prior(Zr)
```
`ρ`はHuberなどのロバスト損失、`wb`は関節検出信頼度・可視性・部位の安定度に基づく重み、`Lb`は本人校正骨長。`E_floor`は接地中の足先・踵が校正床面に近い制約、`E_temporal`は急激な距離ジャンプの抑制、`E_prior`は既知初期距離・身長等の弱い事前分布。頭・手指等の不安定な部位だけに引っ張られないよう、骨盤～膝～足首、肩～肘～手首等の安定部位を優先する。
距離の初期値には、立位で人物の実身長H・画像上の見かけの高さh・焦点距離fyからの近似`Z≈fy*H/h`を利用できる。ただし**しゃがみ・前傾・回転・一部見切れではhが身体の投影高さでなくなる**ため、常時この式だけで距離を更新しない。立位姿勢・複数部位の見かけ長・相対Zを併用する。
### 7.3 単眼距離の状態推定・ロバスト化
1. フレームごとに`Zr`と3D全関節を推定。急に人物が縮んだときには、BBox追跡の揺れ・屈伸・回転・遮蔽による変化か、実移動かを複数の独立特徴で判別する。
2. カメラ校正と本人の骨長を固定基準とし、画像クロップのスケールは距離の基準に使わない。ズームとカメラ移動は姿勢変化と識別できない場合があるため、状態を「未校正」に戻す。
3. 接地判定（踵・つま先の位置／速度、膝角度、連続フレーム）を満たす場合にだけ床面制約を有効化。ジャンプ・つま先立ち・階段移動では足を床へ強制固定しない。
4. 順方向のフィルタ（適応型One Euro Filter、Kalman等）と、録画モード限定の双方向平滑化を別実装する。録画の後方参照をリアルタイム送出へ混入させない。
5. 人物が急に画角外へ出たとき、旧値を短時間予測可能にするが、予測値を実測値と偽装しない。移動中の恒常的な距離ドリフトを監視して校正を促す。
### 7.4 2台以上：三角測量で絶対距離とスケールを確定
- カメラごとの内部K・歪み・外部姿勢・同期関係を校正する。同時刻の**同一関節が2視点以上**で可視の場合に、射線の交点からメートル単位の3D位置を三角測量する。基線長、視線交角、再投影誤差により品質を評価する。
- 2D関節対応点、RTMW3D-Xの相対Z、単眼で求めたZr、骨長、床接地を**統合最適化**する。多視点3Dを高信頼な観測とし、単眼深度を補完とする。三角測量の視線がほぼ平行なら信頼度を下げる。
- 部分視野でも同じ腰や足首が2台に映るならその関節の実測3Dは可能。上半身専用1台・下半身専用1台で**同じ関節が全く映らない**場合、直接三角測量では奥行きが確定しない。各映像の単眼3Dを共通骨格として整合させる**モデル依存の推定**は可能だが、実測と区別する。
- 3台以上の利点は、遮蔽の低減、共通関節が見える確率の向上、外れ値除去である。3台あるだけで自動的に全関節の奥行きが実測可能になるわけではない。
### 7.5 空間座標と「移動」の定義
- 推定したカメラ座標の骨盤位置`Pcamera`を`Pworld=T_world_camera*Pcamera`で部屋のメートル座標へ変換する。床面と初期立位、カメラ設置位置を一致させる。
- 左右移動：`ΔworldX`、前後移動：`ΔworldZ`、上下移動：`ΔworldY`として追跡。**骨盤位置を更新せず関節のみ更新する方式は禁止**。
- 接地中の足がワールド空間で滑る場合、足先の速度・床位置・体幹移動を整合させる。HMDが存在する場合はHMD位置・姿勢を別観測として重みづけし、頭と腰の距離や向きを人体制約へ加える。
- VRChatでの**HMD基準のルームスケール移動**と、スティック等による**ゲーム内ロコモーション（ワールド移動）**は別物。SteamVRトラッカー送出だけでVRChatのプレイヤー全体を自由にテレポート・ロコモーションできるとは主張しない。
### 7.6 距離が確定できない場合の出力
- カメラ未校正・骨長未知・全身が見切れる・角度不足・動いているカメラ等では、`distanceStatus`を`uncalibrated`、`estimatedLowConfidence`、`measuredMultiView`等に分ける。
- 絶対距離が不確かな場合も、RTMW3D-Xの相対3D姿勢は表示可能。SteamVRへ使える品質まで校正できないトラッカーは無効・保留にする。5.14388m等の固定値を有効な現在距離として送出しない。
## 8. 多視点の時刻同期・計算分散
- 動画ファイルでは`video.currentTime`、`requestVideoFrameCallback()`の`mediaTime`等でメディア時刻を基準にする。実機では撮影時刻・受信時刻・推論終了時刻を分け、ブラウザ時計のオフセットとドリフトを推定する。PC時刻をモバイル時計と無条件に同一視しない。
- 静的入力の比較：同じ単一動画をクロップして見切れ耐性を測ることはできるが、**カメラを増やした時の視差の検証にはならない**。真の2視点検証には別位置から同時撮影した映像が必要。
- 最適化：入力フレームの古いキューを破棄し、各カメラ別に「最新有効観測」を保持。統合対象は指定された同期許容時間内に限定し、別時刻の激しい動作を同時観測として扱わない。
- 3ブラウザウィンドウ各1推論：試験対象だが、同一GPU上で複数ONNXセッションを複製するためモデルメモリ負担が増える。基準構成はPCブラウザ1ウィンドウでN映像入力を管理し、RTMW3D-Xを共通WebGPUセッションで時分割する方法とする。バッチ推論はモデルが対応する場合だけ試す。
- ノード3の3D幾何演算・フィルタはWebGPUを必須としない。画像データは可能な限りPCブラウザ内に留め、Node.js統合workerへ送るのは元画像座標の2D関節、相対Z、信頼度、時刻、校正IDだけにする。
## 9. Node.js・SteamVR・VRChatの連携
- サーバー4は最終トラッカー姿勢をVMTのOSCへ変換して`127.0.0.1:39570`へ送る。`/VMT/Room/Unity`等の座標・回転契約をVMT公式ドキュメントに合わせる。VMT Driver/Managerの導入、トラッカーロール設定、SteamVRへの接続は別に検証する。
- 初期ロール：腰・左足・右足。必要に応じ胸・両膝・両肘を追加。トラッカーの位置だけでなく`qx,qy,qz,qw`を生成し、モデルの骨格から算出できない回転軸は低信頼にする。
- 足の方向は踵／つま先／足首と膝方向、腰の向きは左右股関節と肩方向から推定。左右取り違え、カメラ反転、坐標軸の手系差、固定オフセットを校正する。
- VRChatの公式FBTはHMDにアバターが追従し、トラッカー位置との整合・FBT校正が必要。**人物の部屋内絶対位置を求めること**は本システムの必須要件だが、**VRChatのアバターroot移動がその絶対位置に必ず一致すること**はSteamVR/VRC側の仕様・HMD条件を確認したうえで合否判定する。
- SteamVRへの位置・回転送信と、VRChat内の指のアニメーションを分離する。133点は保存し、指の適用経路は別途対応可否を検証する。

## 12. ネットワーク・サンドボックスと無料ホスティング
### 12.1 GitHub PagesとHugging Face
- GitHub ActionsをCI/CDに使い、GitHub Pagesに静的アプリを配信。**GitHub PagesはNode.jsを常駐実行できない**ため、実際の4層サーバーはローカルWindows上のNode.jsで動作する。
- 約369MBのONNXをGitの通常ファイルとしてリポジトリへ直接入れない。GitHubの通常Gitファイル上限100MB、Git LFSはPages配信非対応である。既定モデル取得先はHugging Face、取得後はローカルキャッシュを利用する。
- 旧候補の`https://huggingface.co/akore/rtmw-l-256x192`は2D RTMW-lのSafetensors配布であり、RTMW3D-X 384×288のONNXミラーではない。無条件にフォールバック先へ登録しない。別ミラー採用は同一重み・入力仕様・SHA-256を確認した場合だけにする。
- モデルの取得・外部JS/CSS等の読み込みは**ネットワーク通信である**。Pages動作はオンライン配布モード、完全閉域ではモデル・依存物・UIを事前にローカル保存して`127.0.0.1`で配信する。
- 無料CDNのURLは可変な実行時取得元であり信頼境界ではない。ONNXのSHA-256、JS依存のバージョン固定、可能ならSubresource Integrity、CSPで外部接続先を限定する。
### 12.2 ブラウザとモバイル端末の条件
- 公開PagesからローカルPCへアクセスするとChromeのLocal Network Access（LNA）の`loopback-network`許可が必要になる場合がある。HTTPS Pagesから明示的なローカルIPv4/localhost `ws://`へのWebSocket接続は、対応ChromeではLNA許可を条件として扱える。ただし互換性を優先し、ローカル本番は信頼済みTLSの`wss://`を基本とする。
- iPad/AndroidはPCの`127.0.0.1`には接続できない。PCのLAN IPか`.local`ホスト名へHTTPSでアクセスし、端末が信頼する証明書を用いる。端末のカメラアクセスはHTTPS secure contextとユーザー許可が前提。
- WebRTCのICEはLAN内ホスト候補を使用し、外部STUN/TURNは使わない。端末のAP isolationやOS設定でP2P接続できない場合は、**LAN内TURN/リレーの必要性と遅延を明示**し、外部サーバーに逃がさない。
### 12.3 情報流出防止の現実的境界
- サーバー1・2のオンラインCodex sandboxは外向き通信が許され得るため、**オンラインsandboxという名前だけで外部送信防止を保証しない**。Windows Firewall等による宛先許可制限を設定し、起動時／動作中の外部宛通信を検証する。
- サーバー3はCodexオフラインsandbox、ソケット非公開、親プロセスと制限付きstdioだけ。Node.jsの権限設定単体をセキュリティサンドボックスと同等視しない。
- ネイティブサーバー4はSteamVR OSC用途に限定して127.0.0.1へ送信。外部向けlistenerは作らない。OS/ブラウザ自体が他目的で通信する可能性は独立して管理する。
- 初回のPages/CDNダウンロードを許す**オンライン配布モード**と、キャッシュを使いOSファイアウォールでWANを拒否する**閉域実行モード**を別々に検証。『全パケットをルーターへ跳ね返せば漏えいしない』という前提を採用しない。
- 起動時にネットワーク隔離probe、ループバック横移動probe、HTTPヘッダー・WS Origin・token検証probe、証明書検証を行い、失敗した機能はfail-closedとする。
## 13. 60fpsとRTX 5060 Ti 8GBの検証
- 60fpsの推論目標は「RTMW3D-X本体の1人分推論回数」で測り、動画再生fps・推論結果の描画fps・複数カメラ合計fpsと混ぜない。
- 全体の遅延は撮影→動画デコード／WebRTC→人物検出→ROI→WebGPU推論→SimCC復号→距離最適化→統合→IPC→VMT→SteamVRを段階別に測定する。毎フレーム16.7ms予算に収められるかは実測で判定。16.7msを超えても録画動画PoCは動作可能だが、60Hzリアルタイム追従達成とはしない。
- 8GB VRAMでONNXセッションが多重ロードできるとは限らない。初回モデルダウンロード、WebGPUのモデル初期化、GPUメモリピーク、処理中の拡張モデル・GPU競合、モデルロード失敗を記録。
- サーバー統合が遅くても、単一カメラの推論スループット不足と区別する。映像フレームのキューは原則最新1件とし、時刻が古い姿勢は意図的に破棄する。
- 60fpsが達成できない場合、モデルを自動的に別機種へすり替えず、ROIの検出間引き、入力前処理コスト、データ転送、Session再利用、動画fps、モデルの精度・軽量性とのトレードオフを原因別に記録する。

- LAN内WebRTCで既存2端末から受けた映像をPCブラウザで推論できること。
- 2カメラの時刻対応、校正、共通関節からの三角測量と単眼推定比較。
- オンライン・閉域モードの境界probeとネットワーク通信監査。
### フェーズ3の成果物
- 実機カメラN台の追跡・相対奥行き・ワールドXYZが測定できること。
- VMTドライバ経由でSteamVRの腰・左右足トラッカーが実際に更新されること。
- VRChat上のFBT校正・HMD一致・歩行・前後移動での結果を検証し、入力トラッカー移動とVRChatワールドロコモーションの違いを明記。
## 16. 主要リスクと対応方針
| リスク | 対応 |
|---|---|
| `369MB`のモデル取得遅延・CORS・容量制限 | Hugging Face revision固定、ハッシュ確認、IndexedDB等のキャッシュ、ローカル配布モード |
| RTX 5060 Ti 8GBでRTMW3D-Xが60fps未達 | WebGPU実測、モデルセッション共用、前処理と検出間引き、推論処理内訳の計測。未達を隠さない |
| 推論できても前後移動できない | `relativeZ`と`Zroot`を分離し、単眼幾何校正＋多視点三角測量を実装 |
| しゃがみを後退と誤認 | 身長だけの距離式を常用しない。骨長・接地・時系列を統合、静止比較テスト |
| 下半身のみで全身モデルが破綻 | 見切れ用ROI、仮想BBox、部位マスク、欠測明示。モデルで全身を捏造しない |
| 同一GPUで3ブラウザが競合 | 単一推論セッションの時分割を標準候補、3窓は比較試験のみ |
| WebRTCがLANのみで接続不可 | 端末LANアドレス・HTTPS証明書・ICE host candidate・AP isolation・ローカル中継を検証 |
| GitHub Pages公開時のローカル侵入経路 | LNA権限・CORS・Origin/token・モデルのバージョン固定、ローカル制御APIは必要時のみ |
| Codex sandboxで全ブラウザが保護されるとの誤解 | 子Node workerと通常ブラウザの境界を明示。ファイアウォールで外部宛通信を別途制御 |
| 3D骨格とVRChatプレイヤー移動の混同 | HMD/FBT原点合わせとVRChatロコモーションを独立に検証 |
## 17. 実装順序
1. 指定ONNXの実ファイル、SHA-256、入力・出力名・shapeを記録し、1フレームの推論が公式デモ相当の数値になることを確認する。
2. 動画入力・ROI・2D/相対Zデコード・3D骨格と指・足の描画をブラウザへ実装。
3. 人物の元画像BBoxと関節座標を正しく保存し、単眼`Zroot`を骨長＋カメラKで求める。既定5.14388mを実距離として使わない。
4. 近距離／遠距離／しゃがみ／歩行の実測動画で誤差検証し、結果・ベンチとともにGitHub Pagesに公開。
5. サーバー1・2の限定HTTP/WSSとサーバー3のオフラインIPC、サーバー4のVMT姿勢テストを順に接続。モデル推論の場所はPCブラウザのまま維持する。
6. iPadとP20 LiteでLAN内WebRTCと2視点3D再構成を検証し、カメラ台数と配置の必要性を判断する。
7. 必要と判明した場合にUSB3カメラへ拡張し、SteamVR／VRChatの実機FBTを完成させる。
